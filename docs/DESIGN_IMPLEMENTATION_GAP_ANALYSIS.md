# Hidden Weight 설계·구현 갭 분석과 제작 로드맵

> 기준일: 2026-07-29
> 대상: `docs/` 설계 문서와 `HiddenWeight/` Unity 프로젝트
> 목적: “코드가 존재한다”와 “실제 게임 흐름에서 완성됐다”를 구분하고, 다음 설계·구현 순서를 하나의 기준으로 고정한다.

---

## 1. 결론

### 2026-07-29 구현 업데이트

- 정식 진행 경로를 `Residue_Full → Gaze_Full → Fracture_Full`로 전환했다.
- `SaveService` v1을 추가해 진행도 자동 저장, 이어하기, 임시 파일 교체와 백업 복구를 구현했다.
- 지도·기억 기록·조작·접근성 화면은 스크롤과 키보드/게임패드 포커스를 지원한다.
- Residue/Gaze 지역 UI 아이콘과 의미 기반 상태 문양을 런타임에 연결했다.
- Fracture 룸 콘셉트 15장을 1024px 평면 합성 배경으로 통합하고 현재 방만 렌더링한다.
- 제작된 기억 16개에 화면 제목과 지역별 기억 실을 부여했다.
- BGM이 없는 지역은 임시 앰비언스로 폴백하며, 주요 행동 SFX 이벤트를 연결했다. Unity Editor에서는 BGM만 음소거한다.
- 아래 본문은 최초 감사 당시의 근거와 잔여 과제를 보존한다. 현재 구현 상태는 이 업데이트가 우선한다.

현재 프로젝트는 **핵심 메커닉을 검증한 수직 프로토타입과 세 지역의 구조 블록아웃 사이**에 있다.

- 기본 이동·전투·체력·체크포인트·감정 스킬 3종·자각·지역별 적 행동·보스 공통 로직·엔딩 시퀀스는 코드로 존재한다.
- 잔재는 15방 Full 씬, 실제 아트, 일부 애니메이션, BGM까지 정식 진행 경로에 연결되어 가장 앞서 있다.
- 응시와 균열도 15방 Full 씬과 지역 전용 기믹이 존재하지만, **현재 정식 진행은 구형 4방 씬을 사용한다.** Full 씬은 구조 테스트 대상일 뿐 게임 플로우에 통합되지 않았다.
- 세 지역의 레벨 문서는 방 구조와 UX 기준이 상세하지만, 전체 게임에 필요한 저장, 경제, 지도, 설정, 접근성, 서사 파편 원고, 오디오 구현 규칙은 아직 충분히 설계되지 않았다.
- 문서의 권장 밸런스 값과 실제 ScriptableObject 값이 다르며, 어떤 값이 기준인지 표시하는 단일 진실 공급원이 없다.
- 최근 저장된 PlayMode 테스트 결과는 48/48 통과지만, 대부분 단일 기능·구조 검증이다. 타이틀부터 엔딩까지 정식 씬을 실제로 이어 걷는 회귀 테스트는 없다.

따라서 다음 목표는 콘텐츠를 더 늘리는 것이 아니라 **한 번의 완전한 플레이 세션을 정식 Full 씬으로 끝까지 연결하고, 그 경로의 규칙을 문서와 코드에서 일치시키는 것**이어야 한다.

## 3. 현재 구현 상태

### 3.1 게임 흐름

현재 데이터 기준 정식 흐름은 다음과 같다.

```text
Bootstrap → Title → Prologue → Residue_Full
          → Gaze(구형 4방) → Fracture(구형 4방)
          → Residue_Full 재방문 → Ending → Title
```

의도한 최종 흐름은 다음이어야 한다.

```text
Bootstrap → Title → Prologue → Residue_Full
          → Gaze_Full → Fracture_Full
          → Residue_Full의 최종 백트래킹 목표 → Ending → Title
```

`Zone_Gaze_Full`과 `Zone_Fracture_Full`은 빌드 설정에는 포함되어 있지만 `ZoneData.sceneName`과 `nextSceneName`이 구형 씬을 가리킨다. Full 씬을 직접 로드하면 씬 이름으로 `CurrentZoneData`를 찾지 못할 수 있다. 이 상태에서는 BGM, 자각 안정성, 지역 진행 판정처럼 `CurrentZoneData`에 기대는 로직이 정식 통합 조건을 만족하지 않는다.

또한 균열을 클리어하면 잔재로 돌아온 뒤 **잔재 출구에 닿는 것만으로 엔딩으로 이동**한다. 문서가 의도한 “자각으로 최종 파편/문을 발견하고 능동적으로 마무리한다”는 행동이 엔딩 진입 조건으로 강제되지 않는다.

## 4. 설계에서 부족한 부분

### P0 — 제작을 막는 결정

#### 4.1 정식 씬과 문서의 단일 기준

다음 원칙을 확정해야 한다.

- 정식 지역 씬은 `*_Full`만 사용한다.
- 구형 4방 씬은 `Prototype/Legacy` 폴더로 격리하거나 빌드에서 제외한다.
- `ZoneData`가 씬 이름과 다음 씬을 소유하고, 다른 코드·빌더·테스트는 이를 참조한다.
- 문서의 수치 표에는 `기획 목표값`과 `현재 구현값`을 함께 적거나, 구현값을 자동 추출해 붙인다.
- 변경 이력보다 현재 유효한 결정을 우선해서 읽을 수 있도록 각 문서 상단에 `상태`, `소유자`, `코드 기준`, `마지막 검증일`을 둔다.

#### 4.2 완전한 진행·엔딩 조건

현재의 단순 출구 접촉 대신 아래 순서를 정식 규칙으로 권장한다.

1. 균열 지역 보스 클리어로 `HasClearedFracture` 획득.
2. 잔재 R11/S3로 돌아와 자각으로 최종 흔적 발견.
3. 되감기·자각·예지를 모두 사용해야 열리는 최종 기억 장치 활성화.
4. 마지막 파편을 획득한 뒤에만 R12 또는 별도 출구가 엔딩으로 전환.
5. 엔딩에서 자각을 사용하지 못하고 머무는 경우를 위한 비언어적 힌트와 타임아웃 정책 확정.

이렇게 해야 백트래킹이 단순 왕복이 아니라 세 감정을 통합하는 마지막 플레이가 된다.

#### 4.3 저장·재개 정책

현재 진행도는 프로세스를 종료하면 사라진다. 최소 설계가 필요하다.

- 자동 저장 시점: 체크포인트 활성화, 스킬/자각 획득, 보스 클리어, 숏컷 개방, 지역 전환.
- 저장 내용: 현재 지역, 체크포인트 ID, 스킬, 자각, 파편, 영구 되감기, 조우, 숏컷, 고정 보상, 재화, 체력 조각, 옵션.
- 저장하지 않을 내용: 일반 적 생존 상태, 일시적 발판 위상, 현재 체력과 임시 회복 아이템.
- 사망과 재실행의 차이: 사망은 현재 세션의 체크포인트 복귀, 재실행은 마지막 자동 저장 체크포인트에서 재개.
- 기술 조건: 위치 좌표 대신 안정적인 ID 사용, `saveVersion`과 마이그레이션 함수 포함, 원자적 임시 파일 교체와 백업 1개 유지.

### P1 — 플레이 경험을 완성하는 결정

#### 4.4 전투의 성장 구조

지금 전투는 단일 기본 공격과 접촉 피해 중심이다. 다음을 결정해야 한다.

- 감정 스킬을 전투에서 필수로 만들지, 유리한 선택지로 둘지.
- 일반 적·정예·보스의 체력/피해/경직 규격과 지역별 증가 곡선.
- 회복 아이템 드롭 조건과 체크포인트 회복의 관계.
- 재화의 소비처. MVP에서는 “체력 조각 조합” 또는 “지도/파편 해석 해금” 중 하나만 선택하는 편이 낫다.
- 플레이어 공격 확장은 새 콤보보다 감정 상호작용을 우선한다. 예: 되감기로 보스 장치 복원, 숨죽이기로 특정 공격 회피, 예지로 진짜 예고 구분.

#### 4.5 지역별 학습 곡선

각 지역의 12방을 다음 5개 비트로 다시 태깅해야 한다.

| 비트 | 역할 | 필수 검증 |
| --- | --- | --- |
| 소개 | 새 위협을 안전하게 관찰 | 입력 없이도 규칙을 추론 가능 |
| 연습 | 새 능력 한 가지만 사용 | 실패 후 10초 이내 재도전 |
| 조합 | 이동·전투·능력 2개 결합 | 한 화면에 새 규칙 2개 초과 금지 |
| 숙련 | 선택 보상과 지름길 | 미획득해도 주 동선 진행 가능 |
| 시험 | 보스/최종 퍼즐 | 앞에서 배운 규칙만 사용 |

현재 문서는 방별 의도는 좋지만 “어떤 규칙을 언제 처음 보고, 몇 번 반복하고, 무엇과 조합하는가”를 지역 간 동일 형식으로 추적하기 어렵다.

#### 4.6 서사 콘텐츠 표

별도 `NARRATIVE_CONTENT.md`가 필요하다. 각 파편에 아래 필드를 둔다.

```text
id / 지역·방 / 첫 방문·재방문 / 노출 조건 / 표현 형식
표면 의미 / 재해석 의미 / 연결되는 다른 파편 / 실제 표시 문구
```

세 지역마다 최소한 `도입 1`, `감정의 원인 암시 2`, `왜곡된 자기 해석 1`, `보스 후 재해석 1`의 역할을 배정한다. 주인공의 구체 신원은 숨기더라도 정서적 인과는 있어야 한다.

#### 4.7 입력·옵션·접근성

- Unity Input System 기반 액션 맵과 키 리맵, 키보드/패드 자동 전환.
- 튜토리얼의 `K`, `L` 하드코딩을 현재 바인딩 아이콘으로 교체.
- 마스터/BGM/SFX 음량, 전체 화면, 해상도, 화면 흔들림, 플래시 강도, 자각 탈채도 강도.
- 색만으로 되감기·예지·위험을 구분하지 않도록 형태·애니메이션·소리를 함께 사용.
- 자막/파편 표시 시간, 글자 크기, 보스 재도전 직행 옵션.

### P2 — 콘텐츠 완료를 위한 결정

#### 4.8 오디오 구현 명세

현재 프롬프트와 제작 목록은 풍부하지만 런타임 설계가 없다.

- `AudioMixer` 그룹: Master/BGM/Ambience/SFX/UI.
- 표면별 발소리 식별 방식, 애니메이션 이벤트와 공격/착지 SFX 연결 방식.
- 같은 소리의 랜덤 클립·피치·쿨다운, 동시 재생 제한, 우선순위.
- 보스 예고음은 시각 예고보다 먼저 시작하고 공격별로 식별 가능해야 한다.
- 지역 앰비언스는 방/고도에 따라 스냅하지 않고 크로스페이드한다.

#### 4.9 아트·성능 예산

- 목표 해상도, PPU, 카메라 줌, 스프라이트 최대 크기, 아틀라스 정책을 한 문서에서 고정.
- 방 배경 3레이어 기준의 드로우콜·텍스처 메모리 예산.
- 파티클 최대 수, 보스 VFX 동시 수, 저사양 품질 단계.
- 응시와 균열은 콘셉트 아트에서 게임용 타일·프롭·애니메이션 목록으로 변환하는 제작표가 필요하다.

## 5. 문서와 코드의 주요 불일치

## 6. 구현 로드맵

### 마일스톤 0 — 기준선 고정

목표: 현재 작업 중 변경을 보존하면서 재현 가능한 기준을 만든다.

- 현재 변경분의 의도별 커밋 분리.
- EditMode·PlayMode·macOS 개발 빌드 결과 저장.
- `GAME_DESIGN.md`를 상위 의도, 지역 문서를 레벨 기준, ScriptableObject를 런타임 수치 기준으로 선언.
- 본 문서의 상태표를 이슈/보드로 옮기고 각 항목에 완료 조건 부여.

완료 조건: 깨끗한 체크아웃에서 프로젝트 열기, 테스트, 개발 빌드가 재현된다.

### 마일스톤 1 — 정식 Full 플로우 통합

목표: 타이틀부터 엔딩까지 모든 정식 씬이 연결된다.

1. 응시·균열 `ZoneData.sceneName`과 `nextSceneName`을 Full 씬으로 변경.
2. 씬 상수/빌더/테스트가 문자열을 중복 소유하지 않도록 정리.
3. Full 씬 직접 로드 시 `CurrentZoneData`, BGM, 자각 안정성, 스킬 활성 상태 검증.
4. 구형 씬을 빌드 설정과 정식 테스트 대상에서 제외.
5. 최종 파편/장치를 엔딩 진입 조건에 연결.
6. `Title → ... → Ending` 전체 전환 PlayMode 테스트 추가.

완료 조건: 구형 씬 없이 새 게임을 시작해 세 스킬·자각을 얻고 최종 조건을 충족해 엔딩에 도달한다.

### 마일스톤 2 — 저장·실패·복구 완성

목표: 60~90분 플레이가 종료나 사망으로 유실되지 않는다.

- ID 기반 `SaveData`, 저장 버전, SaveService 구현.
- 체크포인트 자동 저장과 Continue 버튼.
- 사망/지역 재진입/앱 재실행별 상태 초기화 규칙 테스트.
- 보스 직전 체크포인트, 조우 잠금, 숏컷, 되감기 상태 복원 검증.

완료 조건: 각 지역 중간에서 종료 후 재실행해 진행도와 월드 변화가 문서 규칙대로 복원된다.

### 마일스톤 3 — 핵심 플레이 밸런스와 보스

목표: 회색 박스만으로도 처음부터 끝까지 재미와 공정성을 검증한다.

- 감정 스킬 값 A/B 테스트 후 단일 기준 확정.
- 방별 학습 비트와 조우 예산 적용.
- 보스별 고유 단계, 아레나 잠금, 승리 보상, 재도전 루프 완성.
- 재화 소비처 1개와 체력 성장 상한 확정.
- 5명 이상 관찰 테스트: 길 잃음, 사망 원인, 스킬 사용률, 보스 재시도 기록.

완료 조건: 외부 플레이어가 설명 없이 핵심 규칙을 학습하고 막힘 없이 엔딩에 도달한다.

### 마일스톤 4 — 콘텐츠·UX·접근성

목표: 프로토타입을 제출 가능한 게임 경험으로 바꾼다.

- 서사 파편 원고와 환경 변화 적용.
- 지도·옵션·리맵·패드·접근성 UI.
- 응시/균열 최종 아트, 전 캐릭터 애니메이션, 지역 VFX.
- P0/P1 오디오 이벤트와 믹서 적용.
- 로딩·페이드·튜토리얼·보상 피드백 정리.

완료 조건: 모든 필수 정보가 임시 텍스트/플레이스홀더 없이 전달된다.

### 마일스톤 5 — 릴리스 안정화

목표: 빌드 환경에서 성능과 진행 안정성을 보장한다.

- 전체 플로우 빌드 스모크, 저장 호환, 장시간 플레이 테스트.
- 프레임 타임·메모리·로딩 시간 예산 측정.
- 소프트락, 씬 전환 중복, 입력 잠금 미복구, 저장 손상 대응.
- 해상도/화면비/키보드/패드 조합 검증.

완료 조건: 지원 환경에서 새 게임·이어하기·엔딩·재시작을 반복해도 치명적 오류와 진행 불능이 없다.
